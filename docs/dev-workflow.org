* Visão Geral

Este documento descreve o fluxo de desenvolvimento interativo em Elisp no MyEmacs. O fluxo combina inspeção REPL síncrona no IELM, geração e depuração assistida por IA (gptel/Gemini), e validação rigorosa via suíte de testes ERT.

* Ciclo de Desenvolvimento (IA → REPL → ERT)

1. **REPL & Scratch Inline (`C-c D b` / `C-c D r`):**
   - Use `C-c D b` (`+carlos/insert-repl-block`) para envolver expressões em `(when nil ...)` e avaliá-las inline com `C-x C-e` sem colaterais.
   - Use `C-c D r` (`+carlos/ielm-open`) para abrir o IELM e inspecionar símbolos, hooks e estruturas dinâmicas em runtime.

2. **Geração de Testes via IA (`C-c D e`):**
   - Selecione uma função e pressione `C-c D e` (`+carlos/ert-generate-tests`).
   - O gptel usa o prompt centralizado `+carlos/elisp-ert-prompt` para gerar testes no padrão `myemacs-<area>-<desc>` no buffer `*gptel-tests*`.

3. **Validação ERT (`C-c D t` / `C-c D T`):**
   - No arquivo de teste (`tests/<area>-test.el`), use `C-c D t` para executar a suíte do buffer.
   - Coloque o cursor dentro de uma função `ert-deftest` e use `C-c D T` para rodar apenas aquele teste.

4. **Depuração de Erros com IA (`C-c D a` / `C-c D d`):**
   - Ative `debug-on-error` com `C-c D d`.
   - Ao capturar um backtrace ou erro, selecione a região e pressione `C-c D a` (`+carlos/debug-region-with-ai`) para receber diagnóstico de escopo e estado de memória no buffer `*debug-ai*`.

5. **Cuidado com mocks de accessor (2026-08-13):** accessors de =cl-defstruct=
   (=gptel-backend-models=, =magent-thread-turn-usage=, =magent-agent-info-name=)
   são *inlined* no =byte-compile= (vira =aref= + tipo-check) — mock de
   function-cell via =cl-letf= não tem efeito. Prefira: (a) mockar a função que
   *retorna* o struct (=gptel-get-backend= é função normal); (b) expor o dado como
   argumento opcional da função sob teste (=backends=/=local-models=); ou (c)
   testar a *decisão pura* (=+carlos/magent-compaction-decision=) em vez do caminho
   que toca o accessor. Detalhes em =docs/testing-suite.org= (Descobertas de
   Runtime para Mocks).

* Factory Reset (Emergência do Ambiente Oficial)

A receita =just factory-reset= é o botão de emergência máximo: apaga
=~/.config/emacs= inteiro e reclona uma cópia virgem de =origin/main=
(=bin/factory-reset.sh=), seguido de =just install= + =just compile-prod= +
=just check-prod=.

** Fluxo executado

#+begin_src bash
just factory-reset          # interativo
FORCE=1 just factory-reset  # automação (pula guardas)
#+end_src

1. Valida que =$PROD_DIR= existe (override via =EMACS_TEST_DIR=).
2. *Guardas:* aborta se o prod tiver alterações trackeadas não-commitadas;
   pede confirmação interativa (=y/N=) — =FORCE=1= pula ambos.
3. Backup dos arquivos de estado não-regeneráveis para =/tmp=: =bookmarks=,
   =recentf=, =places=, =history=, =savehist=, =custom-file.el= e
   =magent/sessions/= (conversas de IA).
4. =rm -rf= do prod e =git clone -b main= da URL de =origin= derivada do repo
   dev (sem hardcode).
5. Restaura o backup no clone fresco. Em falha após o nuke, o backup fica
   preservado em =/tmp= e o caminho é impresso no erro.
6. Justfile encadeia build completo e boot batch de validação.

** O que NÃO sobrevive

Tudo que não está na lista de backup é descartado e regenerado pelo
=just install= / uso normal: =elpaca/= (reinstall git-based), =tree-sitter/=,
=eln-cache/, vterm-module, transient/history etc. Alterações trackeadas
não-commitadas no prod são PERDIDAS (por isso o guarda dirty-check).

** Guardas estruturais

=testes/factory-reset-test.el= valida estaticamente (sem executar): sintaxe
=bash -n=, presença dos guardas (=FORCE=, =--porcelain --untracked-files=no=,
=trap= do backup, remote dinâmico, =-b main=) e encadeamento =check-prod= na
receita.

* Prompts Centralizados

- ~+carlos/elisp-ert-prompt~: Solicita a geração de suíte ERT completa com naming ~myemacs-~, casos ~should~ e ~should-error~ e mocks com ~cl-letf~.
- ~+carlos/elisp-debug-prompt~: Envia backtrace e código para análise de causa raiz de escopo e estado de memória.
